## 本次新踩的坑（重要）

1. **★ `src/build` 会掩盖 `src/res/` 里缺失的资源**
   `build_lx.sh` 的注释只说它会「新图旧图同时进包」，但实测它还**在悄悄补文件**：
   `src/res/color-v23/` 少了 9 个 appcompat 状态列表（`abc_color_highlight_material` 等），
   历次构建能成功是因为 `src/build/apk/res/color-v23/` 里还留着。
   一旦按脚本要求 `mv src/build` 移走，立刻 `error: no definition for declared symbol`。
   → **教训：判断资源完整性必须直接比对 `original.apk`，不能因为「构建过了」就认为树是全的。**
   修法：`apktool d --no-src original.apk` 反编译出原始 `res/color-v23/`，补回 9 个文件。
   现在 `src/res/color-v23/` = 9 个 appcompat + 3 个应用自有 = 12 个。

2. **javac 在这台机器上默认 GBK**
   源码含中文注释/字符串时报 `编码 GBK 的不可映射字符`。必须 `-encoding UTF-8`。

3. **Windows 上给 javac 传 Unix 路径会静默失败**
   `-cp "tmp/stub;/c/Users/.../android.jar"` → 报 `找不到符号 android.content`（像是缺依赖，
   其实是路径没被识别）。必须 `cygpath -w` 转成 `C:/...` 形式。

4. **不要为了编译一个 Activity 去凑 androidx 的 aar 树**
   `tmp/libs/appcompat.jar` 里**没有** `FragmentActivity`（那是独立的 `androidx.fragment` 制品）。
   正确做法：给 javac 写个桩 `BaseActivity extends android.app.Activity` 就够了 ——
   javac 对继承来的方法按**接收者的静态类型**发指令（`invoke-virtual {p0}, LThemeSettingActivity;->setContentView(I)V`），
   运行时沿真实继承链解析得到，所以桩的父类是谁不影响产物正确性。
   只要保证 `.super Lzd/cornermemory/ui/BaseActivity;` 和 `invoke-super` 指向对就行。

5. **`d8` 加 `--classpath` 指向桩目录可消除 desugaring 警告**
   不加只是 `Type ... was not found, it is required for default or static interface methods desugaring`
   警告，产物字节数一模一样（10816），但加上更干净。

6. **新资源的 id 不要写死**
   apktool 把新 id 分在 `0x7f090357` 起（原版最大 `0x7f090356`），所以写死也能work，
   但新 Activity 里一律用 `getIdentifier(name, type, pkg)` 按名字取，与分配结果彻底解耦。

7. **`CustomToolbar` 的返回键自己会 `finish()`**
   `view_custom_toolbar.xml` 用的是 `@id/back_button`，而 `BaseActivity.setBackImage()` 找的是
   `@id/back_image` / `@id/back_layout` —— 那两个 id 在这个工具栏里**根本不存在**。
   所以新页面**不要调 `setBackImage()`**，直接 `setContentView` 带 `@id/toolbar` 就行。

8. **枚举资源时注意 `.9.png` 双扩展名**
   `os.path.splitext("abc_x.9.png")[0]` 得到 `abc_x.9`，会把 112 个 9-patch 全误判成「新增」。

9. **`AppTheme` 的 parent 本来就是 `Theme.AppCompat.DayNight.NoActionBar`**
   即原版就已经是 DayNight 主题，只是没人切过 `uiMode`。

## 关键判断

- **`id/gif_img`（0x7f090184）不能删** —— `activity_first.xml`（首次启动的隐私协议页）

## 新踩的坑

1. **`invoke-static {p0}` 传 Activity 给 `start(Context)` 是合法的**，ART 会按继承链校验；
   javac 侧用 stub 声明即可。
2. **javac 需要 greendao 的类型才能过检** —— 为 `CjDao`/`AbstractDao`/`QueryBuilder`/
   `Property`/`WhereCondition`/`DaoSession` 各写了一个 stub。
   `detachAll()` / `queryBuilder()` 真实来自 `AbstractDao`，stub 直接声明在 `CjDao` 上就行
   （javac 把 invoke-virtual 的目标写成接收者的静态类型，运行时按虚方法解析照样命中父类）。
   **关键：返回描述符必须与原版一致** —— 照抄 `SplashActivity$4.smali` 里的 invoke 行即可，
   `where`/`orderDesc` 返回 `QueryBuilder`（不是 `AbstractQueryBuilder`）。
3. **`R.array.scr` 是 `0x7f030038`**，Java 里写死成常量（`public.xml` 钉死，不会漂）。
   加了空数组守卫 → `IllegalStateException`，避免「资源 ID 漂了就默默少加载」。
4. **备份文件不能放 `src/smali/`** —— `install_java_smali.sh` 一开始写 `.smali.prev`，
   apktool 报 `W: Unknown file type, ignoring: ...smali.prev`。改放 `tmp/smali_backup/`。
5. **`verify_rebuild.py` 的「资源条目数」要改成净增量**（新增 − 有意移除），
   否则删了 2 个资源会被判成「差 557，预期 559 ❌」。加了 `EXPECTED_REMOVED` 白名单 +
   「有意移除的资源 N/预期 N」一条独立判据。
6. **`verify_darkmode.py` 会因为「备份里有、当前树里没有」而报浅色不等价** ——
   加 `EXPECTED_GONE` 跳过集。
7. **aapt2 `dump xmltree` 的类名不在 `E: activity` 那一行** —— 在紧随其后的
   `A: ...:name(0x01010003)="..."` 行。按行找类名会漏。
8. **校验「调用点在另一调用点之后」不能 `find("方法名()V")`** —— 会先命中
   `.method private xxx()V` 的方法声明。要 find 整条 `invoke-*` 指令。

## 关键判断（都验证过）

1. **必须用 `android:tint` 不能用 `app:tint`。** `BaseActivity` 继承 `FragmentActivity`，
   `LayoutInflater` 没装 AppCompat 的 view factory → `app:` 命名空间属性会被直接丢掉。
   `android:tint` 是 API 21 起 `ImageView` 自带属性，minSdk 21 够用。
2. **PNG 里烤死的颜色不跟主题。** `tab*_normal.png` 是 `#afb5bd`、`tab*_pressed.png` 是 `#1878eb`、
   `back.png` 是纯白。光改布局/文字色不够 —— 必须补 `setImageTintList` / `android:tint`。
3. **`layer-list` + `android:bottom="1dp"` 而不是 `<color>`/`android:gravity`** —— 后两者要 API 23+。
4. **`?attr/` 用在 drawable XML 里可行** —— 本工程已有 113 个 drawable 这么用（opt11 的产物）。
   minSdk 21 起 `Resources.getDrawable(id, theme)` 会解析主题属性；换主题走 `recreate()` → 新 Resources → 缓存重算。
5. **死资源不删。** `layout/back_layout.xml` 是 `@id/back_layout`(0x7f090074) 与

   `toolbar_modern.xml` 用 `@id/toolbar`，`item_card_modern.xml` 用 `@id/card_title`/`@id/card_content`。
   删布局就必须连带删 id 声明、还要先证明没有别处定义同一个 id —— 收益 ~2 KB，风险是 aapt2

## 关键判断 / 新踩的坑

1. ★ **`values-v23/` 放 style 覆盖会整体替换，不是合并**。

### ★★ 本次最大的坑：`<item android:drawable="?attr/xxx" />` 会**崩溃**

opt16 第一次构建出的包，装上模拟器**一点就闪退**。logcat：

```
Caused by: java.lang.UnsupportedOperationException:
    Failed to resolve attribute at index 0: TypedValue{t=0x2/d=0x7f0400f3 a=-1}
  at TypedArray.getDrawableForDensity(TypedArray.java:997)
  at StateListDrawable.inflateChildElements(StateListDrawable.java:182)
Caused by: Resources$NotFoundException: File res/drawable/bottom_nav_tab_bg.xml ...
  at LayoutInflater.parseInclude → createViewFromTag → MainActivity.onCreate(:105)
```

我写的 selector 是：
```xml
<item android:state_selected="true" android:drawable="@drawable/bottom_nav_indicator" />
<item android:drawable="?attr/selectableItemBackgroundBorderless" />   ← 崩在这一行
```

**根因**：`?attr/xxx` 解析出来的结果是 **drawable** 时，`TypedArray.getDrawableForDensity` 拿不到 theme
就**直接抛** `UnsupportedOperationException`（不是退化、不是返回 null，是抛）。而 `?attr` 解析出来是
**颜色**时走的是 `getColor`，拿不到 theme 只是退化成默认值，**不抛**。

⇒ 这就解释了为什么工程里 `edit_text_bg` / `option_border_selector` / `timer_input_field_bg` 等
**14 个 selector 一直没事**（它们的 `?attr` 都在 `<solid android:color>` / `<stroke android:color>` 位置），
以及为什么 `list_item_bgcolor.xml` 把 `?attr/app_light_blue` 写在 `android:drawable` 上也没崩
（`app_light_blue` 解析成**颜色**）。
⇒ 也解释了为什么原来 `bottom.xml` 直接把 `?selectableItemBackgroundBorderless` 写在 **view 的
`android:background`** 上是好的：view 属性走 LayoutInflater 的**带主题** TypedArray，`applyStyle`
会把 `?attr` **彻底解析掉**，根本不会留下 `TYPE_ATTRIBUTE`。

**修法（已落进 opt16）**：
- `bottom_nav_tab_bg.xml`（selector）里**一个 `?` 引用都不留**：

### 两个脚本（都幂等、都自愈）
**`opt17a_tokens.py`** —— 尺寸 token 化。3842 个 dp/sp 字面量 → **165 个 `fw_*` token**，

### 顺手修好 4 个「只认字面量」的核验脚本
token 化/style 化之后，写死字面量的断言会**误报「属性丢了」**。修法统一为
**解析引用 + 展开 style**：
| 脚本 | 误报 | 修法 |
|---|---|---|
| `verify_redesign.py` | 4 条（细线 1dp / 指示条内缩 24dp / 底栏文字色 / tab 背景） | 新增 `dp_of` `has_dp` `styles_in` `style_items` `item_is` |
| `verify_scheme_propagation.py` | 底栏文字色 hint 数 0 | 展开 `@style/Fw*` 的 `0x01010098` |
| `verify_darkmode.py` | 27→74 条「浅色不等价」 | 改用 `collections.Counter` **多重集**比较（位置式 zip 在属性搬家后必然错位；按值排序也错，`#` 排在 `@` 前） |
| `verify_framework.py` | `fw_elev_neg6` / 死 token | 正则补 `-`；`used_tok` 并入 style 文件里的引用 |

★ `style` 在 `aapt2 dump xmltree` 里**没有属性 id**，长这样：`A: style=@0x7f1001a0`
→ 正则必须写 `\bstyle=@(0x[0-9a-f]+)`。
★ `aapt2 dump resources` **会列出 style 的 item**（`0x01010098=?attr/app_text_hint`）
→ 不用反编译就能从成品包里展开 style。
