## APK 静态结构分析（三盲助手 6.2.2）

用户提供了 `三盲助手_6.2.2.apk`（33.56 MB），要求分析结构。

### 做法
不依赖 apktool/jadx，纯 Python 标准库自研解析器，放在 `analysis/`：
- `axml.py` — 二进制 XML（AXML）解析器，含 StringPool + ResXMLTree
- `step1_manifest.py` — Manifest 解析 → `manifest_report.txt`
- `step2_dex.py` — DEX 解析（string_ids/type_ids/class_defs）→ `dex_report.txt`、`classes.txt`
- `step3_arsc.py` — resources.arsc 解析 → `arsc_report.txt`
- 报告：`analysis/APK结构分析报告.md`

### 踩过的坑（重要，复用时注意）
1. `ResXMLTree_node` 的 headerSize=16 **已包含** lineNumber(4)+comment(4)，attrExt 从 `pos+chs` 开始，不是 `+chs+8`
2. `ResXMLTree_attribute` 的 `Res_value` 里 `data` 字段在 `o+16`（size@+12, res0@+14, dataType@+15），不是 `o+12`
3. `mutf8` 解码时 `if/elif` 链要写全，误写成两个独立 `if` 会导致每个 ASCII 字符输出两次
4. `ResTable_package`：typeStrings 在 `+268`，keyStrings 在 `+276`（不是 `+548`）
5. `ResTable_type` / `typeSpec`：`id` 在 `+8`、`entryCount` 在 `+12`、config 在 `+20`，与 headerSize 无关
6. package 之后先是两个字符串池（typeStrings/keyStrings），之后才是 type 分块
7. DEX map_list 的 type 常量：0x2000 class_data, 0x2001 code_item, 0x2002 string_data, 0x2003 debug_info

- 包名 `zd.cornermemory`，versionCode 115 / 6.2.2，minSdk 21 / targetSdk 33，AGP 7.4.2
- 43 Activity（仅 Splash 导出）、1 Service（Tinker）、4 Provider（均未导出）
- 7177 类，其中应用自有 810 类；单 DEX 035，未混淆，SHA-1 校验通过，无壳
- SDK：AndroidX、Kotlin 协程、Glide、Bugly(+Tinker)、OkHttp3、greenDAO(加密)、蒲公英 PGYER、com.zxy.tiny+libjpeg-turbo、Picasso
- assets 占 74%：43MB 三盲公式 JSON + 38MB WCA 333bf 打乱种子 + 离线网页(jQuery/FontAwesome)
- 86 种语言

### 彳亍编码调研结论（重要，已交叉验证）
**绝不凭记忆写表**（Speffz 的教训）。用两个**独立来源**交叉验证后才落表：
- 来源 A：`mist2233.github.io/cube-encoding`（48 字母显式对照表）
- 来源 B：`sohu.com/a/1021386145` 孙氏教程（纯文字规则描述）

把来源 B 的文字规则**翻译成显式表**后与来源 A 逐项比对，24+24 项**全等**；
且两表都恰好用满 `A-Z 去掉 U、V` 共 24 个字母，无重复无缺失。

彳亍核心规则：
- **字母表**：`A-Z` 去掉 **U、V**（读音不便作拼音联想），共 24 个
- **棱块**：顶层 UF→UL→UB→UR 顺时针 A-H；底层 DF→DR→DB→DL 逆时针 I-P；
  中层 FR→FL→BL→BR 为 Q-R / S-T / W-X / Y-Z。**先上面/下面，后侧面**
- **角块**：顶层 UFL→ULB→UBR→UFR 顺时针 A-L；底层 DLF→DBL→DRB→DFR 为 W-M-N / O-P-Q / R-S-T / X-Y-Z
  （注意 DFL 的字母是 **W,M,N** —— 字母顺序被特意打乱）
- **缓冲块**：角块 **UFL(1)**、棱块 **UF(1)** —— **与 Speffz 的角块 URF(0) 不同！**
  （Speffz：角 URF/棱 UF；彳亍：角 UFL/棱 UF）

映射到本项目 Kociemba 编号后（程序推导，非手写）：
```
棱块 index=位置*2+朝向 : GHABCDEFOPIJKLMNQRSTWXYZ
角块 index=位置*3+朝向 : JKLABCDEFGHIXYZWMNOPQRST
```
（对照 Speffz：棱 `BMCI...`、角 `CMJ...`）

→ 推论：**换编码方案必须同时换缓冲块**，否则语义完全不对。
  `EncodingConfig` 里的 buffer 不能再是写死的默认值，要随 scheme 走。

### 新一轮踩坑（重要）
1. **代理端口又变了：6695 → 13860**。判断方法：`env | grep -i proxy`。
   两处都要改：`build.cmd` 的 CB_PROXY_PORT + `cube-bld-gradle-home/gradle.properties`。
2. **★ Gradle 仓库顺序的坑（本次新发现）**：
   Gradle 在某个 repository 报错后会**把整个 repository 禁用**
   （`Repository MavenRepo is disabled due to earlier error`），
   **不会**静静滑到下一个源。所以「官方源优先 + aliyun 兜底」是**失效**的：

   规则写法比每个测试手写更安全（漏写 resetMain 会污染同 JVM 后续测试类）。
4. **`StandardTestDispatcher` 下 `init` 里的 collect 不会立刻执行**。
   测试若在构造 ViewModel 后**同步**调用 `compute()`，`currentScheme` 还是默认值。
   → 必须先 `advanceUntilIdle()`。这个坑在 3 个用例上真实踩到了。
5. `APPLICATION_KEY` 需要显式 import
   `androidx.lifecycle.ViewModelProvider.AndroidViewModelFactory.Companion.APPLICATION_KEY`。

现有测试全是**结构性**检查 —— 字母唯一、落在 A–X、`letterFor`/`locate` 互逆、
面序表尺寸。对调既不产生重复、也不越界、互逆性依然成立。
**字母集合对，落点错，结构测试天生抓不到。**

**根因**：本项目的 `cornerFaceOrder`/`edgeFaceOrder` 采用「先 U/D 面、后侧面」的统一读序。
这对 U/D 层是自然的；但**中层棱块没有 U/D 面**，此时把 F/B 放前面
等于「从背面看这个棱」，左右手性反了。角块同理（D 层角块的 D 贴纸与两个侧贴纸的顺序）。
彳亍表因为其字母本来就按这套读序定义，所以**没有**这个问题 ——
它已用原 APK 数据逐格验证通过。

**修复**：保持 faceOrder 不变，只把受影响格子的字母对调。
依据 speedsolving 维基 Speffz 条目（Seppänen & Holt 2010）的四条官方规则
（每面从视觉左上起顺时针 / 面序 ULFRBD / 字母连续 / D 面先 x2）逐格重推，
再用独立 Python 实现复算，两份逐字符一致。

```
Speffz 角块（本项目读序）：
  URF CMJ   UFL DIF   ULB AER   UBR BQN
  DFR VKP   DLF UGL   DBL XSH   DRB WOT
  => cornerStickerLetters = CMJDIFAERBQNVKPUGLXSHWOT
     （旧值 CMJ DFI AER BNQ VPK UGL XHS WOT，改 4 处）

Speffz 棱块（本项目读序）：
  UR BM  UF CI  UL DE  UB AQ  DR VO  DF UK
  DL XG  DB WS  FR JP  FL LF  BL RH  BR TN
  => edgeStickerLetters = BMCIDEAQVOUKXGWSJPLFRHTN
     （旧值 ...PJ FL HR NT，改 4 处）
```

**SchemeSwitchTest 的 Speffz 期望值同步修正**（用逐格双射重映射，
已自检映射无冲突）：
- corners `GVOFR` → `GVOIR`
- edges `UVSTQXBPFDR` → `UVSNQXBJLDH`
- 彳亍期望值不变（`FJMXS` / `IONZFKGQSCX` / `YTH` / `QOY`）

**新增防线**：`SpeffzStickerTableTest` —— 把 48 张贴纸的字母**逐个写死**，
并单独钉住 8 个易错位置的方向。这是「冻结契约」式测试，
以后再动任何一格都会报出**具体哪一格**。

**教训（写进项目约定）**：
- 编码表这类「字母↔位置」的映射，**结构测试不够**，必须有逐格冻结测试。
- 让「方案切换」纯粹换字母、共用同一张读序表，是这次能把问题定位到
  「表 vs 读序」而不是「编码器 vs 表」的关键。

## 阶段 5（M3 计时与成绩）收尾 + 趋势图 —— 2026-10-09 晚

### ★ 关键事故：app 测试挂死 23 分钟（虚拟时钟 × 真实时钟冲突）

现象：`:app:testDebugUnitTest` 跑了 **23 分钟不返回**，无任何输出/报错，
`test-results/.../binary/output.bin` 为 0 字节。极难定位（看起来只是"慢"）。

根因链条：
1. `TimerViewModel` 起了一个 `while(true) { delay(10); machine.tick(delta) }`
   的 ticker 协程；
2. `delta` 来自 `Clock.nanoTime()` 的**真实**差值；
3. `runTest` 用**虚拟**时钟，`advanceUntilIdle()` 会无限推进虚拟时间 ——
   只要协程里还有 `delay`，就永远等不到 idle；
4. 测试用的 `FakeClock.nanoTime()` 是常量（不随虚拟时间走）
   → 每轮 `delta = 0` → `continue` → **循环永不退出**。

修法（**没有**去伪造"虚拟时间×真实时钟"的耦合，而是分开两条路径）：
- 给 `TimerViewModel` 加构造参数 `tickerEnabled: Boolean = true`；
- `forTesting(...)` 默认 `tickerEnabled = false`，计时完全由
  `tickForTest(delta)` 手动推进；
- 走的仍是**同一个** `TimerStateMachine` + 同一个 `syncState`，
  不存在第二条假路径（这是关键，否则测的是假东西）。

修完：同一套测试 **24 秒**跑完。

### 第二个改正：`runTest` 必须复用规则的 dispatcher

`MainDispatcherRule` 里 `setMain(StandardTestDispatcher())` 是一个实例，
而裸写 `runTest {}` 会**新建另一个**调度器 —— 它的 `advanceUntilIdle()`
推不动 `viewModelScope` 里的协程（因为两者不在同一时间轴），
断言会在"Flow 还没收集到"时随机失败。

统一改为 `runTest(mainDispatcherRule.dispatcher) { ... }`（24 处）。

### 第三个改正：测试期望值写错

`计时中再按一次停表并回到待机` 原本断言停表后 `elapsedMillis == 30_000`。
实际上 `onPressDown` 在 RUNNING 时调用 `recordSolve()`，其中
`takeSolve()` 是**原子操作**（取成绩 + `reset()`），所以 `elapsedMillis` 归零。
改为断言 `elapsedMillis == 0` + 从 `lastSolve.timeMillis` 读 30_000。

> 这是产品语义正确、测试期望过时，不是产品 bug。
> `takeSolve` 的原子性正是为了防"忘调 reset 导致重复取同一笔成绩"。

### 新功能：简易趋势图 `TrendChart`（TimerScreen.kt）

- 用 Compose `Canvas` **手绘**，不引图表库（省几十个类 + 混淆规则）。
- 画两层：单次成绩散点（DNF 跳过）+ 滚动 Ao5 折线（数据源 `ScoreStats.ao5Series`）。
- 纵轴按真实极值自适应并留 8% 余量（否则波动小时贴边框看不出趋势）；
  全值相同时给 1s 最小跨度避免除零。
- 散点用 `forEachIndexed` 拿**存储序**下标定 x，
  不能写 `valid.indexOf(solve)`（两条相同成绩会取同一下标，点会叠住）。
- 数据 < 2 条直接不显示（单点无法成线）。

### 顺手清理

  类级 `@OptIn(ExperimentalCoroutinesApi::class)`（原来 40 条警告）。

### 三个关键结论（都写进 README §4.6）
1. **键首字母只有 6 种：A D G J W X**，对应彳亍角块表的 U/D 面贴纸字母

3. **本项目解析器可吃下整个原库**：因为原库零转体/中层，而
   `Algorithm.parse` 恰好不支持 x y z / M E S。这不是巧合而是必要条件，
   已用测试钉住。若原库含转体就必须先写展开器。
