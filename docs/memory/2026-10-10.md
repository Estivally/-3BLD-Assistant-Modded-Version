# 2026-10-10

## ★★ 用户实测反馈：App 所有按钮点了没反应（最严重的一次事故）

### 现象
用户装上 APK 后反馈：**「这个app用不了，按钮点了无响应」**。
首页六张卡片、返回箭头、右上角设置图标 —— 全部无效。
**不崩溃、不报错、日志干净。**

这是本项目**第一次由真实使用暴露问题**，也说明此前「277 个测试全绿 + 双 APK 出包」
给出的信心是虚高的。

### 根因（确定性 bug，必然失效）

`app/src/main/kotlin/com/dsh/cubebld/ui/CubeBldApp.kt` 里 10 处全是这个写法：

```kotlin
var nav by remember { mutableStateOf(NavState()) }
onClick = { nav = nav.apply { push(Screen.Encode) } }   // ❌
```

链条：
1. `apply { }` 返回**接收者本身** → `nav = nav.apply { ... }` 等于 `nav = nav`
2. `mutableStateOf` 默认 `structuralEqualityPolicy()`，用 `==` 判断「值变没变」
3. `BackStack` 当时是**普通类**，`==` 即引用相等 → 同一实例被判为「没变」
4. → **Compose 不重组** → `screen` 永远是 `Home`

点击事件正常触发、内部 deque 也确实 push 了，**只是界面不知道**。

### 为什么 277 个测试全没抓到
没有任何断言在检查「状态变更后 UI 框架能否感知」。
既有测试都是「调方法 → 看返回值」，而返回值当时是**对的**：
`current` 确实变成了 `Encode`，只是没人通知 Compose。
→ 属于**框架约定层面的错误，纯逻辑测试天然看不见**。
这是本项目第三类「错了也不报错」的问题（前两类：Speffz 字母表镜像、公式库字母体系）。

### 修法（两层，都已落地）

**第一层：状态不可变**（`ui/nav/NavState.kt` 新建）
- `NavState` 改成 `data class`，`push`/`pop`/`reset` 一律返回**新实例**
- 新值与原值结构上必然不等 → Compose 必然重组
- `pop()` 在空栈时返回 `this`（空操作，不抛异常 —— 连点两次返回不能崩）

**第二层：让错误写法无法表达**（同文件 `Navigator` 类）
只靠注释和测试约束调用方不可靠 —— 下一个人照样能写 `nav.apply { ... }`。
所以新增 `@Stable class Navigator`：
- 内部 `var state: NavState by mutableStateOf(initial)`，**`private set`**
- `push`/`pop`/`reset` 自己完成 `state = state.xxx()`，赋的必定是新值
- 调用点变成 `nav.push(Screen.Encode)` —— **没有赋值这个动作可以写错**

`CubeBldApp.kt` 全量重写，10 处 `apply` 全部消除；`BackStack` 类删除。

### 新增测试（14 条）
- `ui/nav/NavStateTest.kt`（9 条）—— 最关键的一条：
  `assertNotEquals("push 必须产生新值，否则 Compose 不会重组", before, after)`

## ★★ 9-patch 重建成功：112/112 全部通过，且语义与原版逐字节一致

### 问题回顾
原 APK 里 112 个 9-patch，apktool 3.0.3 **一个都解不出来**（逐条报
`Could not decode file, replacing by NULL value` 且不写文件）。
上一轮用「循环降级为普通 .png」硬扛 —— 但 112 个里降了 **90 个**，
AppCompat 的 popup 背景 / switch / spinner / 列表分隔线全都会失真。

### 根因（关键认知）
这些 9-patch 是 **aapt v1** 编译的产物。aapt v1 的流程是：

```
带 1 像素边框的源图
  → 从边框解析出可拉伸区间 / 内边距
  → **把边框那一圈像素裁掉**，写出「净图」
  → 把九宫格信息塞进自定义 PNG 块 npTc
```

而 **aapt2 是重写版，只认边框像素、不读 npTc**。
所以这些文件在 aapt2 眼里就是「尺寸莫名小、边框像素随便什么色」的坏图。

三条报错各自对应一个具体缺陷：
| 报错 | 原因 |
|---|---|
| `image must be at least 3x3 (1x1 image with 1 pixel border)` | 净图只有 1×1（原图 3×3，边框被裁） |
| `top-left corner pixel must be either opaque white or transparent` | 角上是**内容像素**（原本那圈是透明边框） |
| `found an invalid color` | 边框位置是内容像素，不是纯黑 |

### ★ npTc 布局（对照 112 个文件 100% 验证通过）

```
byte 0        was_deserialized
byte 1        numXDivs
byte 2        numYDivs
byte 3        numColors
@4   u32 **小端**   xDivsOffset   （恒为 32）
@8   u32 **小端**   yDivsOffset   （= 32 + 4*numXDivs）
@12  u32 ×4        内边距 (左, 上, 右, 下)   ← 就是这个，不是 offsets！
@28  u32 **小端**   colorsOffset  （= yDivsOffset + 4*numYDivs）
@xDivsOffset   numXDivs 个 u32 **大端** → xDivs
@yDivsOffset   numYDivs 个 u32 **大端** → yDivs
@colorsOffset  numColors 个 u32 **大端** → colors
```

**踩过的坑**：一开始把 @12 当成 colorsOffset（值是 0），怎么都算不通。
真相是 aapt v1 只对**数组内容**做了 `htonl`（所以数组是大端），
**偏移量按本机字节序**写出（小端）；而 @12..27 那 16 字节放的是内边距。

### ★ aapt2 的边框校验规则（用合成图实测反推，见 probe_aapt2.py）

| 位置 | 合法值 | 违规报错 |
|---|---|---|
| 四个角 | **必须全透明**（全零字节） | `top-left corner pixel must be either opaque white or transparent` |
| 边框标记 | **必须不透明黑** `(0,0,0,255)` | 红 → `found unexpected optical bounds (red pixel)`；白 → `found an invalid color` |
| 尺寸 | ≥ 3×3 | `image must be at least 3x3` |

（消息里那句 "opaque white" 有误导性 —— 实测**透明**就通过。）

### 做法
`rebuild_9patch.py`：
1. 解 npTc → xDivs / yDivs / 内边距
2. 画布放大 2 像素，内容搬到 (1,1)
3. 顶边按 xDivs 涂不透明黑，左边按 yDivs 涂不透明黑（**内容区坐标 + 1**）
4. 底边 / 右边按内边距涂标记
5. 四角一律全透明
6. `ct=0`（灰度）/ `ct=2`（RGB）**必须升级**为 `ct=4` / `ct=6`，否则边框没法透明
7. 输出**不带 npTc** 的干净 PNG，让 aapt2 自己从边框推导

### 验证（这才是关键，不能只看「能编译」）
`compare_9patch.py`：拿 aapt2 资源转储把原 APK 的短文件名还原成资源名，
再逐条比对**原版与重建版编译产物**的 npTc：

```
原 APK 9-patch: 112
语义完全一致  : 112
不一致        : 0
无法比对      : 0
```

拉伸区间与内边距**全部逐字节一致** → 说明重建在语义上等价，不只是「能过编译」。

### ★★ 差点漏掉的第二个坑：内边距字段顺序

第一次跑通后我换了个角度复查（不再比 npTc 尾部数组，而是比 @12..27 那 4 个数），
发现 **112 个里有 10 个内边距对不上**，规律是中间两位互换：

```
spinner         原=[0, 48, 0, 0]  新=[0, 0, 48, 0]
bga_sbl_shadow  原=[0, 19, 33, 32] 新=[0, 19, 19, 32]
popup(mdpi)     原=[8, 9, 8, 9]   新=[8, 8, 9, 9]
```

**根因**：npTc 的 @12..27 存 4 个 u32，顺序是 **(左, 右, 上, 下)**，
不是直觉上的 (左, 上, 右, 下)。我按直觉解读，于是「右 48」被写成了「上 48」。

**怎么钉死的**：`probe_padding_order.py` 做受控实验 ——
造一个内边距刻意不对称的源图（左=2 右=3 上=5 下=4）交给 aapt2 编译，
读回 npTc@12..27 = `[2, 3, 5, 4]` → 顺序确认为 (左, 右, 上, 下)。

**教训（重要）**：第一次的「112/112 一致」是**比错了字段** ——
`parse_nptc` 返回的 `colors` 是 npTc 尾部那个 `numColors` 长的数组，
它并不编码内边距；真正的内边距在 @12..27。
**「验证通过」也要检查验证的到底是不是那个东西。**

### ★★ 第三个发现：apktool 原生解码会丢内边距

apktool 3.0.3 **有时能自己把 9-patch 解出来**（产出的就是带边框的合规源图，
aapt2 直接能过）。所以「112 个全部解不出」这个前提**并不是每次都成立** ——
本次实测复现了两遍都是 0 失败，无法重现上一轮记录的 112 失败。

但**不能因此省掉重建步骤**：用 `border_to_divs.py` 从 apktool 产出图的
边框像素反推九宫格，与原版 npTc 比对：

```
apktool 原生解码 vs 原版  →  一致: 94   不一致: 18
不一致全是内边距被清零：
  abc_btn_switch_to_on_mtrl_00001 / 00012  各 5 个密度
  abc_popup_background_mtrl_mult           4 个
  abc_menu_hardkey_panel_mtrl_mult         4 个
```

即 **apktool 能还原可拉伸区间，但会把内边距丢掉**（popup 的 24px 文字内缩、
menu 面板的 12px、switch 滑块的 5px/11px 全变 0）。
表现是 popup 里文字贴边、控件内容位置偏移。

→ 所以无论 apktool 解得出解不出，`rebuild_9patch.py` 都要跑。
它在文件没有 npTc 时**静默跳过**（说明 apktool 已解对且无需修正），
有 npTc 时从 `src9_orig/` 取源重建。

### 附带修掉的坑
- **扩展名与真实格式不符**：3 个 `.png` 实为 JPEG、1 个 `.png` 实为 WebP
  → aapt2 报 `failed to read PNG signature`。`fix_ext.py` 只改这几类；
  另有 15 个 `.webp` 里是 JPEG，但 **aapt2 不校验 `.webp`**，保持原样不动。
- **`@null` 占位条目冲突**：apktool 给每个被丢弃的 9-patch 写了
  `<drawable name="X">@null</drawable>`，还原真实文件后冲突
  （`has a conflicting value for configuration`）→ `dedup_drawables.py` 精确删除。
- **降级副本残留**：早期 `fix9patch.sh` 改过名的 90 个 `.png` 会和新还原的
  `.9.png` 撞名 → `dedup_9patch.py` 用**内容哈希比对原 APK** 确认是副本后才删。

### ★ 工具链发现
apktool 3.0.3 的 fat jar 里**自带 `prebuilt/windows/aapt2.exe`**，
`jar xf apktool-cli.jar prebuilt/windows/aapt2.exe` 就能抽出来单独用。
→ 单文件编译验证只要 ~1 秒，不用每次跑完整重打包，**迭代速度提升一个数量级**。
（aapt2 版本 2.20-eng.202610）

### ★ 关于「批量删除」的沙箱约束（重要）
`rm -rf src`（188 MB、上万个文件）会触发钩子
`[SAFE_DELETE_BULK_CONFIRM_REQUIRED]`。
→ 流程改成**不删除**：apktool 用 `-f` 覆盖式写入（同输入 + 同版本输出确定，
不留脏文件）；需要「从零开始」时用 `CLEAN=1` 把旧树 **mv 走**而不是删。
少数必须清理的残留（改名过的图片）由 `fix_ext.py` 精确单文件处理。

### 幂等性设计
`restore_9patch.py` 把 aapt v1 的**原始字节另存一份**到 `src9_orig/`；
`rebuild_9patch.py` 每次都从 `src9_orig/` 取源、写回 `src/res/`。
因为重建会覆盖 `src/res` 里的文件（覆盖后就没了 npTc），
不留原始档案的话第二次跑就取不到源了。

## 原 APK 内置联想图调查（同日）

**背景**：用户拿 Anki 导出的 `所有牌组.txt`（576 条联想词）要配套图片，问「原 APK 里已有的就别重做」。

### 核心发现
1. **原 APK 自带整套 576 张联想图**，藏在 `res/drawable/`，资源名 = 小写编码（`drawable/a`、`drawable/ab`…）。
   之前查 `assets/` 没找到，是因为它在 `res/` 而不是 `assets/`。
2. **映射链路**：`Dictionary.smali` 的 `initDic()`（内置词表）+ `initPic()`（编码→drawable ID），
   ID→资源名→混淆文件 靠 `D:\Program\dsh\rebuild\res_dump.txt`。
   解出的资源名如 `drawable/do1`（DO 用了两个资源名之一）。
3. **命名差异**：内置表单字母用 `AA`/`BB`/…，Anki 表用 `A`/`B`/…，是同一槽位，比较前必须映射。
4. **差异结果**：完全同名可复用 **206**，同义待确认 **16**，需新图 **354**。
5. **内置集本身违反 50 kB**：49 张 >50 kB，最大 XW 219.5 kB；可复用的 206 张里也有 14 张超标。

### App 图片机制（从 smali 解出，重建/重写都要遵守）
| 项 | 值 |
|---|---|
| 自定义图目录 | `lx_pic_custom` |
| 保存格式 | JPEG 质量 85，最大边长 1280 px |
| 文件名 | `<编码>_<SHA256>.jpg` |
| 资源包扩展名 | `.lxres`（ZIP），前缀 `3bld_helper_lx_assets_` |
| 包内结构 | `manifest.json` + `images/<大写编码>.jpg` |
| manifest 键 | packageType(`lx_custom_assets`) / version(1) / exportTime / itemCount / items[] |
| items[] 键 | code / hasCustomRemark / customRemark / hasCustomImage / imageEntryName / imageHash / imageSize |

### 筛选成本
按 21% 可用率，每词需看 30–50 张才能凑够候选 → 354 词约**上万张图需人工过目**，比生图更费。
