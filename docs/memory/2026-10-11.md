### ⚠ 两处推翻了自己先前的结论（都要记住）

**1. 「锁内 I/O」是 jadx 反编译错误，不是真问题。**
`ReadSolutionLookup.readFirstAlgorithmFromInfo` 的 Java 反编译看着是
`synchronized { ... readFirstArrayValue(...) ... }`（I/O 在锁内），
但**原始 smali 里 `monitor-exit` 在调用之前**，I/O 本来就在锁外，是标准双检锁。
→ **jadx 在异常处理器切分监视器区间时会误重建 `synchronized`**。
判断锁范围**必须读 smali**，不能信 jadx。
真实问题是：`build()` 在 `ReadSolutionActivity.onCreate` **主线程**调用（无线程/协程），
而 `readFirstArrayValue` 是线性扫描，parity 未命中要扫 29.96 MB。

**2. 「转动态 WebP」在 minSdk 21 下不可行。**
- Android 原生只在 **API 28+** 支持动态 WebP（`ImageDecoder`/`AnimatedImageDrawable`）
- Glide 的 `AnimatedImageDecoder` 也只在 `SDK_INT ≥ 28` 注册（`RegistryFactory.smali` 守着）
- API 21–27 上 `BitmapFactory` 解动态 WebP **返回 null / 失败**，不是「显示静态首帧」
→ 那个页面会**图直接不显示**。已改回「保持 GIF 重编码」。

### 体积估算的教训
原报告写「576 张图可省 8.2 MB」，因为拿 `图片-最终/`（源图目录，16.65 MB）当基线。
**实际拆成品包：466 张本来就是 WebP、65 PNG、45 JPEG，共 12.76 MB**，真实收益只有 2.55 MB。
→ **体积估算必须基于成品包里的实际文件。**

### 第 3 项实际做法（派生「首元素」公式库）
这些 `*AlgToInfo.json` 每条存全部算法（parity 每条 50 条），但代码
`readFirstArrayValue()` **只取数组第一个字符串元素**；离线 HTML 才需要全量。
→ 生成 `parity/edge/cornerAlgToInfoFirst.json`（0.58/0.06/0.04 MB）给 App 用，
smali 只改 3 处路径字面量，**零逻辑改动**。
扫描量 29.96/6.91/0.80 MB → 0.58/0.06/0.04 MB。
等价性：全部 **13856 条逐一自检**通过（都是字符串数组，无空数组、无空首元素）。
脚本 `make_first_alg_assets.py`。`twistsAlgToInfo.json`（2.56 MB）是同一模式，未做。

### ⚠ 原版资源路径是缩短过的（新增结构认知）
实测 `original.apk` 的 `res/` **根目录下有 1312 个条目**（形如 `res/aB.xml`、`res/zX.png`），
**完全没有 `res/drawable/`、`res/layout/` 这些目录** —— 这是 AGP 的
「资源路径缩短 + 名字混淆」。apktool 重打包一律用规范路径，
所以**两个包的 ZIP 条目名不可直接对照**（差 1313 条，全部是路径规范化），
这不是缺陷（资源表按 ID 映射，功能无影响）。核验脚本已写成显式判据，避免每次误报。

### 又一次「批量删除撞钩子」（同类第 2 次）
`SAFE_DELETE_BULK_CONFIRM_REQUIRED`（阈值 50）在本次踩了两处：
1. `apply_lx_update.py` 原实现「先删同 stem 旧文件再写新的」→ 重跑时 576 次 `os.remove` 直接断在第 1 步。
   **改成幂等**：先编码成字节，与现有文件比对，一致就跳过（不删不写）。现在报「改写 0 / 跳过 576」。
2. `verify_lx_content.py` 用 `shutil.rmtree` 清 `tmp/verify_lx_smali`（8680 文件）→ 词表校验被打断。

   所以必须让目录「不存在」，移走效果一样）。
→ **结论：凡是要清上千文件的目录，一律用「移走」而不是「删除」。**

### 新踩的坑（都属「错了也不报错」那一类，这是第 4、5 次）

1. **`opt10` 重跑会把字面色暗色覆盖整批抹掉。**
   暗色映射原来从「字面量扫描」推；第一次跑完站点全变成 `@color/lit_*`，`scan()` 就空了
   → 重跑写入的 `values-night` 只剩 22 条语义色（116 条字面色没了），
   而且脚本报告仍显示「成功」。
   **修法**：加 `existing_lit_pairs()` 从 `values/colors.xml` 读回已有 `lit_*`，
   再断言「写入条数 == 应写条数 且 > 100」。已验证重跑 md5 不变。
   → **教训：脚本的输出若依赖「扫描当前状态」，重跑就会自我抹除。
   凡是「已抽取 → 再生成覆盖层」的两段式脚本，第二段必须能从第一段的产物读回。**

2. **`values-night-en` 目录名不合法。** 资源限定符必须按规范顺序：语言在前、night 在后
   → 只能叫 `values-en-night`，否则 aapt2 报 `invalid configuration 'night-en'`。

3. **`verify_rebuild.py` 拿 `confs` 判「新增资源」是错的。** `confs` 只收录**有 `(config)` 值行**
   的资源；`string`/`color` 这类单值资源在 dump 里没有 config 行 → 全被误判成新增（一次多算 1038）。
   改成用**全量资源名集合**（所有 `resource 0x…` 行）。

### 领域知识（新）

- **Android 资源限定符优先级：语言 > 夜间模式。**
  原版有 `res/values-en/`（自带 `AppTheme` + 21 色，用的是旧 Material 默认色 `#3f51b5`/`#ff4081`），
  所以英文设备上 `values-en` 会盖掉 `values-night` → 深色下「黑字黑底」。
  必须再补 `values-en-night/`。
- **`BaseActivity` 继承的是 `androidx.fragment.app.FragmentActivity`，不是 `AppCompatActivity`。**
  所以 AppCompatDelegate 的夜间模式机制不生效；但 **framework 层的 `values-night` 仍然有效**
  —— 只要 `android:configChanges` 里没有 `uiMode`（本项目只有 `orientation|screenSize`），
  系统切深色时会重建 Activity 并选到 `values-night`。
- **`AppTheme` 换 DayNight 是「浅色零风险」的**：`values/styles.xml:1297` 里
  `Theme.AppCompat.DayNight.NoActionBar` 的 parent 就是 `Theme.AppCompat.Light.NoActionBar`；
  `values-night/styles.xml` 才把它接到 `Theme.AppCompat.NoActionBar`。
- **字面色必须先抽资源才能被 `values-night` 覆盖**（`values-night` 只覆盖命名资源）。
  抽的时候要**按属性分角色**：实测 5 个值跨角色（`#ffffff` 当底色 12 次 / 当白字 2 次）。
- **`grey` 的角色冲突**：108 处当底色、21 处当文字，深色下要求相反 →
  把 21 处文字改用 `@color/lit_text_6b7280`（同值），底色走 `grey` 的 night 覆盖。
  同理 `@color/white` 当背景的 31 处 → `@color/surface`（同值 `#ffffff`）。
  例外：`cube_fill_white.xml` 是魔方白面，保持 `@color/white`。
- **魔方贴纸色不能动**：`cube_fill_{white,red,blue,green,orange,yellow}` 引用
  `@color/{white,red,blue,green,orange,yellow}`，这些是语义色不是界面色 → night 里不覆盖。
- **smali 会按资源 ID 用语义色**：`CubeNetColorManager` 用 `white`/`red`，
  `TimerFragment` 用 `black`/`text_primary`/`colorPrimaryDark`/`green_text`，
  `MainActivity` 用 `line`/`white`。所以 night 覆盖对代码路径也生效（这通常正是想要的），
  但**改 `white` 会同时改魔方白面** → 所以选择「不覆盖 `white`，只把当背景用的 31 处改指 `surface`」。

### Baseline Profile 结论更正（重要）
`APK优化建议.md` 原写「baseline.prof 只有 2545 B，基本是空的 / 是 stub」——**错**。
实测它是真 profile：偏移 17 起 zlib 流解出 **19956 B**，版本标记 `0x000b`、
类数 136、方法数 6410、dex 位置 `classes.dex`、类/方法计数 4392/61058。
2545 B 只是压缩后体积。
**但它已过期**：偏移 8 处的 u32 dex crc32 = `0x0c26b618` == **原版** dex 的 crc32；
重建版 dex（9,203,440 B，crc32 `0xd80eb27e`）对不上 → profile 不生效（不崩，只是白搭）。
重生成需要 Gradle 源码工程 + `androidx.benchmark` + 真机；本机 `adb devices` 为空，做不了。
