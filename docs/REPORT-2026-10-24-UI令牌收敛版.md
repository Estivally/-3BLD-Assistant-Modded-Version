## 二、为什么能"底层逻辑不变"

这套 UI 的颜色本来就是**三层**结构：

1. **`?attr/app_*`（172 个）** —— 布局和 drawable 里 **2612 处**引用，全部跟随 8 套 ThemeOverlay；
2. **`@color/lit_*`（182 个）** —— 字面量，不跟随主题；
3. **drawable 内裸 hex** —— 只剩 1 处（`bottom_nav_tab_ripple.xml`）。

因为第一层已经铺满了，所以这次**一个 attr 名都没改**，只改它们的**取值**：

```
<item name="app_lit_bg_006366f1">#006366f1</item>   ← 名字保持原样（历史包袱）
                                    ↑ 只动这里
```

2612 处引用自动跟着变，**不可能出现"改了颜色忘了改引用"的编译断裂**。同理，尺寸只改 `@dimen` 的**值**，不改 token 名，也不碰布局里的引用。

### 语义角色的来源

角色判定**只看 attr 名字里的基准 hex**（作者当初是照着靛蓝方案写的，名字里的 hex 就是他的意图）：

- 在 indigo 浅色这一套上做一次 **ΔE 吸附**（阈值 9.0），得到一张全局 role map；
- 8 套 overlay 共用这张表，**不读当前值** → 天然幂等，连跑两次结果完全一致；
- 每个角色再派生：`_container` = mix(role, card, 0.12)（浅色填充）、`_soft` = mix(role, card, 0.35)（描边）、`text_body/secondary/tertiary` = mix(text_primary, card, 0.86/0.60/0.38)。

### 描边为什么要单独一档

第一轮收敛把徽章的**底色**和**边框**都归到了 `success_container` —— 边框和底色同色，边框直接消失了。

扫 `src/res/drawable*` 得到证据：98 个 attr 用于形状，其中 **stroke-only 38 个、solid-only 55 个、两者兼用仅 5 个**（且都是 `app_line`/`app_black` 这类语义色，非 `app_lit_*`）。**描边色和填充色在命名上本来就是分离的**，所以可以安全地给描边单独一档 `*_soft`，每套 overlay 多 18 处改动。

徽章文字色走 `res/color/remember_assoc_badge_on_text.xml` → `@color/green_text`，**全工程只有这 1 处引用**，所以改动是外科手术式的：

### 2. 深色顶栏"两种品牌表达"——复查后判定为**不是缺陷**

审计阶段曾把「深色顶栏 `#1B1E33` vs 浅色顶栏 `#4F46E5`」记为品牌断裂。复查 `theme_schemes.xml` 后确认：`app_bar_bg` 本来就是**每套 scheme 各配一个值**，深色配深色栏是正确设计，不是漏改。

| teal | #0F766E | #10231F |

| graphite | #334155 | #1C2026 |

真正需要修的是**深色下按钮文字**：`on_primary` 在深色态取页面底色（而不是白），否则 `#818CF8` 底 + 白字只有 1.50:1。这条已由 `derive()` 处理。

### 深色分层（6.4.2 新增）

**问题**：深色下 `app_background` `#121417` 与 `app_surface` `#1a1d21` 只差 **1.09:1**，卡片"融"进页底，整页的信息层级消失——对话框尤其明显（卡片和背后的页底看起来是同一块）。浅色下卡/页是 1.04:1，但靠阴影 + 1.24:1 描边兜底，不构成问题。

**做法**（仍严格在"只改值"的边界内，没有新增 attr、没有改布局）：

1. `ui_palette_spec.py` 新增 `contrast()` 与 `ensure_separation(fg, bg, target=1.25)`：朝白色按 2% 步进提亮，**只抬不压**，达到目标即停，因此幂等。
2. `opt20_palette_gen.py` 在 `anchors_of()` 里只对 `.Night` 方案做三级抬升：`app_surface` 对 `app_background` ≥ 1.25，`app_line` 对 `app_surface` ≥ 1.20；写盘循环里对这两个 attr **强制写入**（它们是锚点，原本一律 keep）。
3. **踩过的坑**：`mix()` 返回元组首字节是"混色比例 alpha"，不是颜色 alpha。第一版直接沿用，`app_surface` 被写成 `#0f282b2e`（6% 透明）——而它同时被当 textColor 用在 32 处（6.4.1 的主色按钮标签），会直接隐形。改为硬编码 `(255,)` 后修好。

**结果**（`tools/ui_audit.py` 的 `elevation` 节，阈值 1.15）：

| indigo.Night | `#121417` | `#282b2e` | `#333940` | **1.09 → 1.30** | 1.22 |
| teal | `#f5faf9` | `#ffffff` | `#e2ecea` | 1.05（靠阴影） | 1.21 |

| violet | `#faf8fd` | `#ffffff` | `#ebe6f2` | 1.05（靠阴影） | 1.23 |
| violet.Night | `#150e1e` | `#2c2536` | `#3c3248` | **1.28** | 1.22 |

## 五、没做的，以及为什么

6.4.1 复查后，原来的四条「未做」有两条**被重新定性为不需要做**，另外两条**给出了硬理由不做**：

| 项 | 6.4.1 状态 | 结论 / 原因 |
| --- | --- | --- |
| `fw_size_*` 75 档 → ≤12 档 | **明确不做改值** | 这 75 个 token 的**名字里就写着数值**（`fw_size_48`）。改值 = 名字说谎（`fw_size_48` 变成 44dp）；改名要同时动 `public.xml` 和 smali —— `ThemeSettingActivity.smali:308/:827` 会用 `const-string "radius_sm"` 这种**字符串查表**取尺寸，改名即运行时崩。所以只做**按用途分组审计**（`ui_dimens_spec.fw_size_report()`）：square 32 档 / control 23 档 / box 16 档，各自列出非 4dp 网格的成员，供以后按组一次性重排。 |
| 裸 dp 566 处 → 16dp 网格 | **重新定性：不是债** | 逐属性统计后发现 524 处是 `layout_width`/`layout_height`，且取值只有 `0dp` 和 `1dp` 两个 —— 前者是 `layout_weight` 的占位，后者是分隔线，**本来就不该上网格**；剩下 34 处 margin/padding **全部是 0dp**。真正的节奏债在 `values/dimens.xml`：133 个应用自有语义 token 里有一批 3/5/9dp、13/19/21sp 的连续微调，已由 `opt22_dimens_rhythm.py` 吸附 **24 处**。 |
| 趋势页空状态层叠 | **已修**（6.4.1） | 见下方「三、P0 修复 · 3」。 |
| 其他页图标 6 种色相 | **保留** | 图标本来就已走 `?attr/app_lit_tint_*`，且深色有对应浅色变体（`475569 → #cbcdd0`）。这是作者有意的彩色图标风格，属于"沿用现有设计风格"，强行统一成单色是主观决策，留给你定。 |

6.4.0 报告里列的两个「已知观感问题」，6.4.1 都已消掉：

- **主色按钮文字 4.47:1** → 锚点下探到 indigo-600（`#4F46E5`），白字 **6.29:1**；深色那一半见 P0-3。
- **「换一组」与「开始作答」并排不等高** → 根因不是阴影，是**两个不同的 token**：输入框 `main_answer_height 50dp` vs 按钮 `main_action_height 48dp`。`opt22` 把 50 吸附到 48 后两者同高。

## 六、复现方式

```bash
cd D:/Program/dsh/rebuild
SKIP_LX_UPDATE=1 bash build_lx.sh        # 第 1.5 步会自动跑 opt20 / opt21 / opt22 / opt23
PYTHONIOENCODING=utf-8 python tools/ui_audit.py   # 验收口径（含 elevation / icon_contrast / vector_literals）
```

`opt20` 现在承担三件事，都是幂等的：① 172 个 attr 的取值按语义角色重写；② 深色 `.Night` 的 `app_surface` / `app_line` 三级抬升（`ensure_separation`，只抬不压）；③ 提示文字极性覆盖（`app_text_hint` 浅 `#8a000000` / 深 `#8affffff`）。重跑第二次必须是 "已是目标状态，无需改动"，否则说明脚本不幂等。

- `opt20_palette_gen.py` / `opt21_dimens_ladder.py` / `opt22_dimens_rhythm.py` / `opt23_on_primary.py` 都是**幂等**的：已是目标状态时输出「已是目标状态，无需改动（幂等）」或「需要翻转标签色：0 处」，0 改动。本次四个脚本连跑两遍，第二遍全部 0 改动。
- 备份写在 `tmp/`，**不能写进 `src/res/values/`** —— aapt2 会把 `.bak-*` 当非法资源路径，直接 `Execution failed (exit code = 1)`。
- `build_lx.sh` 里加了 `export PYTHONIOENCODING=utf-8`：控制台是 GBK，opt 脚本打印 ✅ 会 `UnicodeEncodeError` 把第 1.5 步整条链打断。
- 验收口径：`python tools/ui_audit.py`（每套 overlay 的独立色数 / 裸 dp / 裸 hex / dimens 档位 / 关键对比度）。

### 执行过程中新发现并修掉的两个 P0

这两条不在原报告里，是这次动手时用脚本查出来的，比原 P0 更严重：

- **P0-3 · 深色下主色按钮白字只有 2.98:1**。深色方案 `app_colorPrimary` 是亮紫 `#818CF8`，而布局里 32 个主色按钮的标签是硬编码 `@android:color/white` → 白字压亮紫，低于 AA 4.5。修法：`opt23_on_primary.py` 把「浅色深底白字、深色变亮底」的标签改成 `?attr/app_surface`（浅 `#FFFFFF` / 深 `#1A1D21`）→ 深色 **5.67:1**。
  - 为什么不新增 `app_on_primary` attr：新增 attr 会让 aapt 重新分配 attr ID，而 `src/smali` 里的 `R$attr` 常量是硬编码的，加一个 attr 就可能把后面所有 ID 顶掉 → 编译过、运行崩。`app_surface` 的极性正好就是 onPrimary。
- **P0-4 · 提示文字 1.32:1**。8 套 overlay 的 `app_text_hint` 都是 `#61xxxxxx`（38% alpha 的浅灰蓝），压在卡片上只有 1.32:1（浅）/ 1.50:1（深），输入框 placeholder 基本看不见。修法：`opt20` 新增极性覆盖 `POLARITY_OVERRIDE = {'app_text_hint': ('#8a000000', '#8affffff')}` → **4.61:1 / 5.79:1**。

顺带纠正 6.4.0 审计脚本里的两条**误报**（探针取错前景色）：

- 「次要文字 1.61:1」是假的 —— `app_grey` 在布局里 108 处**全部**当 `background`（0.1dp 分隔线），0 处当 `textColor`。真正的次要文字是 `app_text_secondary`（116 处）→ **5.74:1 / 6.84:1**。
- 「主色按钮文字 1.50:1」也是假的 —— 探针用了 `app_bar_text`（`#A5B4FC`），而真实标签是白色。真实值 2.98:1，是 P0-3 修掉的那个。
