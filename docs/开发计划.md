# 三盲助手 · 开发计划

> 依据：`analysis/APK结构分析报告.md`（三盲助手 6.2.2，包名 `zd.cornermemory`）
> 基线：versionCode 115 / versionName 6.2.2 / minSdk 21 / targetSdk 33 / AGP 7.4.2
> 代码规模：7177 类（应用自有 810 类），单 DEX，未混淆
> 数据规模：assets 83.75 MB（占 APK 体积 74%）

---

## 0. 关键前提确认（开工前必须先定）

报告的静态分析给出了**结构**，但没有给出**业务语义**。以下三个问题会实质性改变工作量，建议先拍板：

| # | 问题 | 影响 |
|---|---|---|
| Q1 | **目标是什么？** ①重写一个同类产品 ②在原 APK 基础上做二次开发/改版 ③只做子集（比如只要公式查询+计时器） | 决定是「从零建工程」还是「反编译改造」。原 APK 未混淆、可读性高，反编译改造路径成本更低但法律风险更高 |
| Q2 | **公式数据从哪来？** 直接用原 APK 的 `assets/*.json`（43MB），还是自己整理？ | `parityAlgToInfo.json` 单文件 29.96 MB，是产品护城河，重做等于从零积累 |
| Q3 | **是否保留 WCA 打乱同步？** 需要走 `worldcubeassociation.org` 公开 API | 决定是否要网络层 + 缓存 + 离线降级 |

**默认假设**（未确认时按此推进）：目标是「①重写同类产品，V1 覆盖核心功能，公式数据复用原 assets」。

## 1. 目标与技术选型

### 1.1 产品定位
面向魔方三阶盲拧（3BLD）学习者的**训练 + 记忆 + 公式查询**工具。核心价值主张：**完全离线可用**（公式库与 WCA 打乱全部内置）。

### 1.2 技术栈建议

原 APK 的技术栈有几处明显欠债，新项目建议直接对齐现代化方案：

| 维度 | 原 APK（6.2.2） | 新项目建议 | 理由 |
|---|---|---|---|
| 语言 | Kotlin + Java 混合 | **纯 Kotlin** | 消除混编 |
| UI | XML + Fragment | **Compose + Navigation** | 44 个 Activity 里有 12 个是 Cs/Fx 排列组合，Compose 可用一个参数化 Composable 替代 |
| 架构 | 无明确分层 | **MVVM + Repository** | 原代码 `App` 类长达 4 个内部类做缓存，说明缺乏分层 |
| 数据库 | greenDAO（含加密库） | **Room** | greenDAO 已停止维护；`GreenDaoCompatibleUpdateHelper` 说明历史迁移很痛苦 |
| 图片 | **Glide + Picasso 并存** | **仅 Coil** | 原方案冗余约 700 个类，白白增大体积 |
| 依赖注入 | 无 | **Hilt** | — |
| 最小 SDK | 21 | **24**（或 26） | Android 5.0 已无必要，可省大量兼容代码 |
| 目标 SDK | 33 | **35** | 上架 Google Play 强要求 |
| 混淆 | **未开启 R8** | **必开 R8 + 资源缩减** | 报告明确指出反编译可读性高 |

> 若 Q1 答案是「②反编译改造」，则技术栈保持不变，只做增量修补（见 §7 的降级路径）。

## 3. 分阶段路线图

### 阶段 0 · 技术预研（1 周）

- [ ] 确认 §0 的三个前提问题
- [ ] 验证公式数据结构：用 Python 抽样解析 `parityAlgToInfo.json` / `edgeAlgToInfo.json`，产出数据结构文档
- [ ] 验证 `assets/*.html` 离线网页能否独立运行（jQuery 3 + FontAwesome 5，纯静态）
- [ ] 决策：离线公式库用 **JSON 预编译为二进制 / SQLite** 还是保持按需流式解析（29.96 MB 单文件全量加载会 OOM，必须流式）
- [ ] 验证蓝牙计时器协议（`GanSmartTimerProtocol` / `QiyiSmartTimerProtocol`，需要真实设备）

**产出**：数据结构说明 + 技术选型确认单 + 加载性能测试报告

### 阶段 1 · 地基（2 周）

- [ ] 建 Android 工程骨架（Kotlin + Compose + Hilt + Room + Coil）
- [ ] 三层分层：`data`（Repository + Room + DataSource）/ `domain`（算法与用例）/ `ui`
- [ ] Room schema，对应原 greenDAO 的 5 个实体：

```kotlin
@Entity Cj            // 成绩记录（对应 db.Cj）
@Entity RememberCj    // 记忆训练成绩（对应 db.RememberCj）
@Entity WcaCompetition// WCA 赛事（对应 db.WcaCompetition）
@Entity WcaScramble   // WCA 打乱（对应 db.WcaScramble）
```

- [ ] 数据迁移：若沿用原用户数据，需实现 greenDAO → Room 的迁移（参考 `GreenDaoCompatibleUpdateHelper` 的思路）
- [ ] 国际化框架（先做 zh-CN / en，其余 84 语言按需补）
- [ ] 崩溃监控接入（替换 Bugly；**不要**保留 Tinker 热修复，见 §6）
- [ ] 基线 Profile（原 APK 有 `baseline.prof`，说明启动优化是刚需）
- [ ] CI：GitHub Actions / 自建流水线，跑 lint + 单测 + 打包

**产出**：可运行的空白 App + 分层骨架 + CI 绿

### 阶段 2 · 核心算法层（2 周）—— **最高风险，优先攻坚**

这一层是产品真正的技术壁垒，且可**脱离 UI 独立测试**。

- [ ] 移植/实现 **Kociemba 二阶段求解器**（对应 `min2phase` 包，6 个类：`CoordCube` / `CubieCube` / `Search` / `Tools` / `Util`）
- [ ] 移植/实现 **三阶段求解器**（对应 `threephase` 包，12 个类：`CenterCube` / `CornerCube` / `EdgeCube` / `Edge3` / `FullCube` / `Moves` / `Search` / `Util` / `Center1~3`）
- [ ] 坐标系统（`CoordinateUtil` / `WcaCoordinateHelper` / `CoordinateKeyValue`）：角块/棱块编码 ↔ 位置 ↔ 坐标 的双向映射
- [ ] 编码字典（`Dictionary`）：编码表 → 记忆词/图形的映射
- [ ] 公式匹配（`ReadSolutionLookup`）：由魔方状态反查公式
- [ ] **单元测试**：用已知打乱序列做回归，覆盖率目标 ≥ 80%

> 求解器是纯算法，可先在 JVM 上跑通再接 UI。原 APK 未混淆，类结构清晰，移植成本可控。

**产出**：算法库 + 测试报告 + 性能基准（单次求解耗时）

### 阶段 3 · M1 编码记忆训练（3 周）

- [ ] 改读训练（`MotifyReadActivity`）
- [ ] 排序训练（`MotifySortActivity` + `SortCode` / `CodeSortAdapter`）

## 6. 必须修复的安全与合规问题

报告 §9 明确列出了 6 项，逐条给出行动项：

| # | 问题 | 严重度 | 行动项 |
|---|---|---|---|
| 1 | **`PGYER_API_KEY` / `PGYER_FRONTJS_KEY` 明文硬编码在 Manifest** | 高 | 移除蒲公英 SDK，或改为服务端代理 + 白盒加密。密钥绝不入仓 |
| 2 | **Bugly / 蒲公英使用 HTTP 明文上报** | 高 | 替换为 HTTPS 的崩溃监控（自建 Sentry / 友盟+ / Firebase Crashlytics）。若必须保留，用 `networkSecurityConfig` 白名单**显式禁止**明文 |
| 3 | **Tinker 热修复 + `REQUEST_INSTALL_PACKAGES`** | 高 | **移除 Tinker 与 `REQUEST_INSTALL_PACKAGES`**。这是最危险的供应链风险面（可运行时下发代码 + 应用内安装 APK）。走应用商店正常发版 |
| 4 | `READ_PHONE_STATE` 权限 | 中高 | 若仅用于设备标识，改用 `Settings.Secure.ANDROID_ID` 或 App Set ID，删除该权限 |
| 5 | `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` | 中高 | 只在 Android 12+ 蓝牙扫描时**按需申请**，并声明 `neverForLocation`，不要开机就要 |
| 6 | 未开启 R8 代码混淆 | 中 | 必开 R8 + `shrinkResources`。原 APK 类名完整保留，等于把实现白送 |
| 7 | `allowBackup=true` | 中 | 改为 `false`，或提供 `dataExtractionRules` 白名单 |
| 8 | greenDAO 加密库 | 中 | 若用了加密库，确认密钥从 Keystore 取而非硬编码；迁 Room 时用 SQLCipher |
| 9 | FileProvider authority 撞车 | 低 | 原 APK 同时声明 `zd.cornermemory.fileprovider` 与 `zd.cornermemory.fileProvider`（大小写差一个字母），修为单一 authority |
| 10 | `READ_LOGS` 权限 | 低 | 对第三方 app 实际无效，直接删除 |
| 11 | 证书 CN=aaa 占位 | 低 | 用正式开发者证书签名，且**妥善保管 keystore**（现代 Android 无法换签名） |
| 12 | `android.support.v4` 遗留 183 类 | 低 | 清理残留依赖，全量迁移 AndroidX |

## 7. 备选路径：反编译改造（若 Q1 选 ②）

原 APK 的有利条件：**未加壳、DEX 完整可校验、类名未混淆、资源虽被缩短但可还原**。

低风险路径：
1. `apktool d` + `jadx` 反编译（报告中的自研解析器可作交叉验证）
2. 只做**增量修改**：修安全问题、换崩溃监控、开混淆、升 targetSdk
3. 保留 greenDAO 与现有 UI，不重构

**风险提示（必须让决策者知情）**：
- **法律风险**：反编译他人 APK 二次分发，可能侵犯著作权。若这是他人产品，需先取得授权
- 资源名已被 `shrinkResources` 缩短（`res/4B.gif`、`res/0L.xml`），**回编译后资源引用可能出错**，需要相当工作量修复
- 43 个 Activity 的 XML 布局与 `resources.arsc` 中的 87,196 条资源项无法高保真还原为可读形式
- 热修复（Tinker）与加固代码的存在会让回编译更复杂

结论：**除非已获授权且目标只是小改动，否则建议走新项目重写路径。**
